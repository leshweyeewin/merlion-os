## 1. Executive Summary

MerlionOS integrates live data feeds from Singapore public APIs (LTA DataMall, NEA API, data.gov.sg), partitioned Google Cloud BigQuery economic analytics, and community broadcast channels. All data panels in the **SG Hub Dashboard** load on-demand when clicked and display a **"Last synced"** SGT timestamp. This reference documents the REST endpoints, schemas, caching rules, and linear-regression forecasting algorithms powering SG Hub live dashboards.

## 🩺 Automated data-source monitoring

The scrapers above all **degrade silently** — if a source changes its HTML/JSON, the parse comes back empty and the pane quietly serves committed sample data (flipping an internal `is_live` flag) rather than crashing. To catch that, [`scripts/healthcheck.py`](../scripts/healthcheck.py) runs on a daily schedule via the [`Data source monitor`](../.github/workflows/monitor.yml) GitHub Action:

- **Scraper canaries** — re-runs each live scraper (HDB Newsroom, HDB BTO launch tables, ICA Newsroom, IRAS due dates, IRAS latest updates) and **structurally validates** the result: right shape, non-empty, expected fields present. A renamed key or changed CSS class → empty parse → caught (something a plain HTTP-200 check would miss). Reachability, though, splits by source:
  - **ICA / IRAS** endpoints *do* accept the GitHub-runner IP, so the runner scrapes them live. A structurally-valid-but-`is_live=False` fallback there means the markup actually changed → **WARN**.
  - **HDB Newsroom / BTO tables** sit behind a WAF that **403-blocks cloud/datacenter IP ranges, including GitHub runners** (the same block that pushed the live deploy from Cloud Run to Render). A not-live HDB result *on the runner* is therefore the expected WAF fallback, **not** a regression — so `check_hdb_news` returns **SKIP** (never WARN/FAIL) to avoid a daily false alarm.
  - **Real HDB breakage is still caught — measured from where the feed actually works.** `monitor.yml` sets `HEALTHCHECK_TARGET_URL=https://merlion-os.onrender.com`, and the healthcheck first fetches the **deployed Render app's [`/api/health`](../server.py)** (Render's AWS egress isn't WAF-blocked, so HDB fetches live there). For the WAF-blocked sources it then uses those **remote** statuses — tagged `[Remote via Render]` in the report — instead of the runner's own SKIP. Net effect: the runner never false-alarms on HDB, but a genuinely broken HDB scraper still surfaces via the Render probe. If the remote fetch fails, it falls back to the local per-scraper checks.
- **BigQuery health + staleness** — for each of the 3 loaded tables (`sg_housing.hdb_resale_prices`, `sg_employment.job_vacancy_by_industry`, `sg_employment.occupational_wages`) it verifies the table exists, has a sane row count, and — reading `MAX(period)` straight from the table — how many months/years behind "today" the freshest loaded period is. Past each dataset's lag tolerance it flags **"a newer edition is likely out — re-run the loader"**, the actionable "new data available" signal.
- **Rules-freshness (hand-maintained policy figures)** — a third staleness class the scrapers and BigQuery don't cover: dollar figures typed in by hand from official pages (benefit amounts and income caps in [`tools/eligibility.py`](../tools/eligibility.py); stamp-duty, loan-to-value and grant rates in [`tools/upfront_cost.py`](../tools/upfront_cost.py); CPF Retirement Sums and indicative payouts in [`tools/cpf_life.py`](../tools/cpf_life.py); and life-event journey steps and links in [`tools/life_events.py`](../tools/life_events.py)) that drift at each Budget. Each such module publishes `RULES_YEAR` / `RULES_LAST_REVIEWED` / `RULES_REVIEW_BY`, and the monitor (`POLICY_CHECKS`) **WARNs once today passes the review-by date** — a re-verify reminder (the app keeps working), not a breakage. All four are set to review by **2027-02-28**, just after the SG Budget, so the WARN lands right when the fresh figures are out.

On any failure or staleness warning the workflow opens (or refreshes) a single labelled `data-monitor` GitHub issue with the full report, and auto-closes it once a later run is all-green. No external service and no new secrets — it reuses the `GCP_SA_KEY` the deploy already uses and the built-in `GITHUB_TOKEN`.

## 🔔 Watchlists & alerts

The **My Alerts** tab (in the SG Hub) lets a visitor subscribe to a threshold on any signal the dashboard already tracks and be notified only when it crosses — turning the dashboard from something you check into something that reaches out. Backed by [`tools/alerts.py`](../tools/alerts.py) (SQLite store + evaluator) and [`tools/alert_delivery.py`](../tools/alert_delivery.py) (delivery adapters).

| Watch type | Fires when | Source (reused, cached) |
|---|---|---|
| **COE premium** | a category's premium goes below/above your threshold | `compute_coe_bidding_stats()` |
| **PSI / air quality** | national PSI crosses your threshold | `fetch_weather_data()` |
| **MRT line** | LTA reports a disruption on your line | `fetch_lta_train_alerts()` |
| **HDB resale** | your town's median moves ±X% from when you subscribed | `compute_hdb_resale_stats()` |
| **BTO launch** | a launch appears in your town | HDB newsroom scrape |
| **IRAS deadline** | a filing deadline falls within N days | `fetch_iras_due_dates()` |

- **One evaluator, two channels.** A daemon thread sweeps every ~5 min (`ALERTS_INTERVAL_SECONDS`), reusing the same memoised payloads the panels serve (so it adds no upstream load), records an in-app notification, and fans out to the user's linked **Web Push** and **Telegram** channels. **State-based dedupe** means a standing condition (PSI stuck above 100) fires once, not every sweep.
- **No accounts.** Identity is a browser-generated `client_id` in localStorage; every request is scoped to it. Telegram binds to the same id via a 6-digit **pairing code**; Web Push binds a `PushManager` subscription.
- **Telegram bot (two modes, one handler).** The bot (`tools/telegram_bot.py`) links a chat when the user sends the pairing code (or taps the `t.me/<bot>?start=<code>` deep link). It runs either by **long-polling** (`TELEGRAM_MODE=polling`, the default — a daemon thread, no public URL, ideal for local dev) or by **webhook** (`TELEGRAM_MODE=webhook` + `POST /api/alerts/telegram/webhook`, for a public HTTPS host like Render; register it with `py -3 scripts/telegram_setup.py set <url>` and authenticate it with `TELEGRAM_WEBHOOK_SECRET`). Commands: `/start [code]`, a bare 6-digit code, `/stop` (unlink), `/check <message>`, `/help`. **Any other free-form message is answered by the AI Co-Pilot** (`run_chat_loop`, single-turn) — so Telegram is a full conversational surface for government-services questions, not just an alert sink — except a message containing a link, which is auto-scanned for scams instead.
- **Config (all optional, graceful when absent):** `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` for Web Push (generate with `py -3 scripts/gen_vapid_keys.py`), and `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME` (+ `TELEGRAM_MODE`, `TELEGRAM_WEBHOOK_SECRET`) for Telegram. Without them the in-app feed still works; the extra channels simply stay hidden/disabled. Storage path is `$ALERTS_DB_PATH` (default `data/alerts.db`; attach a Render persistent disk to survive redeploys).

## 🛡️ Scam checker

Paste a suspicious SMS / message / URL → a heuristic risk verdict (`tools/scam_checker.py`, endpoint `POST /api/scam/check`, UI in the **Scam Checker** SG Hub tab, plus the Telegram bot).

- **Signals.** Brand **impersonation** is the strongest — a message name-dropping Singpass / a bank / IRAS / SingPost but linking to a domain that isn't that org's real one (the brand token baked into the host, or the brand named while the link is independently suspicious). Plus URL shorteners, lookalike/**punycode** domains, raw-IP hosts, throwaway TLDs (`.xyz`, `.top`, …), `http`, and text signals (urgency/threats, OTP/credential asks, prize/parcel/refund lures, off-platform contact). Scores sum into `high`/`medium`/`low`/`none` tiers; impersonation or a campaign match short-circuits to `high`.
- **Trusts real `*.gov.sg`.** Nobody but a SG agency can register one, so a `gov.sg` link is never flagged as impersonation — a genuine IRAS message mentioning Singpass doesn't false-positive.
- **Campaign cross-reference.** Best-effort, cached (1 h) match against recent `@scamshieldalert` posts (`recent_scam_advisories()`), so a currently-circulating scam is flagged. Degrades to pure heuristics on any fetch failure.
- **Deterministic + offline engine.** `check(text)` uses no network/LLM, so it's testable and works even when rate-limited. Output is always **guidance, not certainty** — every verdict carries the same safe-action advice and a ScamShield (1799) report link, and a "looks ok" result never reads as "this is safe". Nothing pasted is stored.

## 💰 Benefits Finder (eligibility screener)

A short profile → the government schemes the person is likely eligible for (`tools/eligibility.py`, endpoint `POST /api/eligibility/check`, UI in the **Benefits Finder** SG Hub tab).

- **Schemes (v1):** GST Voucher – Cash, CDC Vouchers, Workfare Income Supplement, Baby Bonus, SkillsFuture Credit, Enhanced CPF Housing Grant. Each declares its checkable rule (income/age/Annual-Value/property caps, citizen-only gating, situational flags like new-child or buying-a-flat), an indicative amount, a "why", an official apply link, and a dated rule note.
- **Inputs:** citizenship, age, gross monthly income, home **Annual Value** (optional — "unsure" → the scheme returns `maybe` rather than guessing), properties owned, marital status, employment, expecting/newborn, planning to buy an HDB flat.
- **Output:** per-scheme `eligible` / `maybe` / `not` (sorted, with reasons) plus a headline "you may be eligible for N schemes worth ~$X" (only `eligible` schemes count toward the total, split into recurring-yearly vs one-time).
- **Framing.** Deterministic and offline (`assess()` is pure functions, no network/LLM → testable/stable). Explicitly **informational, not an official determination or financial advice**: amounts are indicative ("up to X"), dated to the published rules year, and always paired with the official link. Nothing is stored.

## 🏠 Home upfront-cost calculator

A purchase price + short buyer profile → the one-off cash/CPF needed before you get the keys (`tools/upfront_cost.py`, endpoint `POST /api/upfront-cost/estimate`, UI in the **Home Cost** SG Hub tab).

- **Computes:** **Buyer's Stamp Duty** (IRAS progressive schedule), **Additional Buyer's Stamp Duty** (by residency × residential properties already owned — a citizen's first home is 0%), the **down-payment** at the 75% loan-to-value limit split into its minimum-cash portion (5% for a bank loan, none for an HDB loan) and the CPF-OA-payable remainder, and an indicative **Enhanced CPF Housing Grant** offset for eligible first-timers (reusing the Benefits Finder eligibility gates).
- **Inputs:** purchase price, residency, properties already owned, loan type (bank / HDB), household (family / single), gross monthly household income (optional, for the grant), first-timer flag.
- **Output:** a headline **cash-needed-at-signing** figure plus a line-item breakdown (BSD / ABSD / down-payment / grant), the loan amount, the CPF-coverable portion, a best-case net-after-grant, and the assumptions made — each duty linked to its official IRAS/HDB page.
- **Framing.** Deterministic and offline (`estimate()` is pure arithmetic, no network/LLM → testable/stable). Explicitly **informational, not a quote or financial advice**: rates are dated to the published year, stated as charged on the higher of price or market value, and paired with the official calculators. The stamp-duty / LTV / grant figures are hand-maintained, so the module publishes `RULES_*` constants watched by the [data monitor](#-automated-data-source-monitoring). Nothing is stored.

> The three tools below (Home cost, CPF LIFE, COE bid-timing) plus the [Benefits Finder](#-benefits-finder-eligibility-screener) make up the **forward-looking "should-I" suite** — turning the dashboard's backward-looking data into decisions a resident actually faces (can I afford this flat, what will I retire on, is now a good time to bid).

## 👛 CPF LIFE payout projector

Expected Retirement Account savings at 55 → an indicative monthly retirement payout (`tools/cpf_life.py`, endpoint `POST /api/cpf-life/estimate`, UI in the **CPF LIFE** SG Hub tab).

- **Computes:** which **Retirement Sum** tier the savings reach — Basic / Full / Enhanced (BRS / FRS / ERS) — an **indicative CPF LIFE Standard-Plan monthly payout range** from age 65, the **gap to the next tier** and what reaching it would add, and a **deferral uplift** (~7%/year) if payouts start after 65 (up to 70).
- **Inputs:** expected RA savings at 55, payout-start age (65–70), current age (optional).
- **Framing.** Deterministic and offline. Explicitly **informational, not financial advice or an official CPF projection** — payouts are actuarially determined, so figures are indicative ranges dated to the published cohort year and always paired with the official **CPF LIFE Estimator**. Sums/payouts are hand-maintained → `RULES_*` constants watched by the [data monitor](#-automated-data-source-monitoring). Nothing is stored.

## 🚗 COE "should I bid now?" read

A deterministic bid-timing read layered onto the existing COE panel (`compute_coe_bid_timing()` in [`tools/transport.py`](../tools/transport.py), surfaced in the **Transit & Transport** tab's COE card).

- **Computes:** per vehicle category, combines the **recent premium trend** (last ~6 exercises) with the **linear-regression forecast** for the next round into a **heating / cooling / flat** read — reusing data the panel already fetches (no extra source, no LLM).
- **Framing.** Explicitly a **read on where the premium is heading, not advice on whether to bid** — the card carries that caveat, and stays silent for any category without enough history. Deterministic, so it's covered by unit tests over synthetic series.

## 🧭 Life-event journeys

Guided, ordered checklists for major Singapore life events (`tools/life_events.py`, endpoints `GET /api/life-events/journeys` and `GET /api/life-events/journey/{key}`, UI in the **Life Events** SG Hub tab).

- **Journeys:** Welcoming a Newborn, Getting Married, Buying Your First Home, Losing Your Job, Planning for Retirement, When Someone Passes Away.
- **Steps:** Each step maps out the action, agency, timing, a short detail, an official link, and — where relevant — deep-links into another MerlionOS tool (Benefits Finder, Home Cost, CPF LIFE, Scam Checker) to help the user complete the action.
- **Framing.** Deterministic and offline catalog lookup. Explicitly **informational, not legal or financial advice**. The steps, agency, and links are hand-maintained → `RULES_*` constants watched by the [data monitor](#-automated-data-source-monitoring). Nothing is stored.
